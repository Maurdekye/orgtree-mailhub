# Mail hub v2.0.0

v2 is the mail hub rewritten in Rust with its records in PostgreSQL. Phase 1
(this document) is a **faithful port**: the same HTTP protocol, credentials,
refusals, custody and receipt rules, configuration and data layout as the v1
Python hub, so every existing client — Orgtree 3.x and 4.x, `hubtool.py`
and its MCP server, the operator page — works unchanged. The differences
that remain are deliberate and listed below, each with the reason and
whether it was measured.

Phase 2 (hubchat: per-device keys, multi-device delivery, kept history, a
searchable directory, long messages, resumable transfers) adds to the
protocol beside v1's routes; the additions are described in
[v2-additions.md](v2-additions.md), and the few a v1 client can notice are
listed below.

## What runs

One binary, `orgtree-mailhub`:

| command | does |
|---|---|
| `orgtree-mailhub` / `orgtree-mailhub serve` | runs the hub (full app on `HUB_PORT`, the API-only public listener when `HUB_PUBLIC` is set) |
| `orgtree-mailhub migrate` | brings the database schema up to date and exits |
| `orgtree-mailhub import-sqlite [PATH] [--merge]` | imports a v1 store (`hub.sqlite3`, or a v1 data folder) and prints the report |
| `orgtree-mailhub healthcheck` | exits 0 when the hub on `HUB_PORT` (local) answers `/healthz` — the container healthcheck |
| `orgtree-mailhub version` | prints the version |

Source: `hub/` (crate `orgtree-mailhub`, library `mailhub`); the operator
page is `hub/static/index.html`, compiled in. The v1 Python server left the
tree once Phase 1 was reviewed; the tests that still run it (the side-by-side
comparisons, hubtool's own suite) take it from git history at 79a7c51
(`tests/v1_reference.py`). `hubtool.py` (the chat client) is unaffected and
needs only Python's standard library.

## Configuration

Every v1 variable keeps its name, default and meaning: `HUB_NAME`,
`HUB_PORT` (7370), `HUB_BIND`, `HUB_PUBLIC`, `HUB_PUBLIC_BIND`, `HUB_DATA`
(`/data`), `HUB_RETENTION_DAYS` (30), `HUB_ORG_RETENTION_DAYS` (45),
`HUB_MAX_FILE_BYTES` (1 GiB), `HUB_RUNTIME_CONFIG_FILE`. New in v2:

| variable | default | meaning |
|---|---|---|
| `HUB_DATABASE_URL` | — (required) | the PostgreSQL connection string, URL (`postgres://user@host:5432/db`) or key=value form. The hub keeps its tables in the schema `mailhub`, so it can share a database. No TLS to the database in v2.0.0: use a local or private-network server. |
| `HUB_DATABASE_PASSWORD` | — | the database password, kept out of the URL (no percent-encoding; a host passes it apart). Overrides a password in the URL. |
| `HUB_DB_POOL` | 32 | database connections the hub may hold |
| `HUB_PUBLIC_PORT` | 7371 | the public listener's port (fixed in v1; the default is unchanged) |
| `HUB_IMPORT_SQLITE` | on | import `HUB_DATA/hub.sqlite3` at the first start (see Upgrading) |
| `HUB_LOG_VERBOSE` | off | `1`: every handler's call and return and every SQL statement on stderr |
| `HUB_LOG_FILTER` | — | a `tracing` filter overriding the verbosity, for diagnosis |

## Storage

- PostgreSQL, schema `mailhub`: `identities` (v1's `orgs`), `messages`,
  `attachments`, `hub_meta` (schema version, import record). Hub-clock times
  are `timestamptz` at millisecond precision and are rendered exactly as v1
  rendered them; what a client claims (`sent_at`, a receipt's `at`) is kept
  verbatim as text, as v1 kept it. Addresses and ids compare bytewise.
- `messages.n` is v1's SQLite rowid: the tie-break after `received_at` in
  every ordering and the operator page's paging cursor. A v1 store's numbers
  are kept by the import.
- Attachment bytes stay files under `HUB_DATA/blobs/<id>`, the v1 layout, so
  a v1 data folder's files are used in place.
- One hub process per database: presence and long-poll wake-ups live in the
  process (as in v1), so a second process on the same database refuses to
  start rather than seeing half the picture.

## Upgrading from v1

Replace the image (or binary) and restart, as before — v2 just needs its
database. On its first start against an EMPTY database, the hub imports
`HUB_DATA/hub.sqlite3` in one transaction (all or nothing), writes
`HUB_DATA/v2-import-report.json` and records the import in `hub_meta`, so it
never imports twice. The SQLite file is only read and is kept as the
rollback. Clients notice nothing: addresses, fingerprints, queued mail,
receipt states, attachment rights and message numbers carry over.

A database that already holds hub records is never imported into
automatically; `orgtree-mailhub import-sqlite PATH --merge` imports beside
existing records (rows whose address or id already exists are skipped and
counted). An import from another folder copies the blob files across.

What PostgreSQL cannot hold is repaired and counted in the report's
`anomalies` rather than failing the start: a NUL character removed from text,
an unreadable timestamp (v1 never writes one) replaced by the import time.

### Docker

`compose.yaml` adds a `postgres:18` service (not published on any host port;
only the hub reaches it) and a second volume, `orgtree-hub-db`. Set
`HUB_DB_PASSWORD` in `.env` before the first `docker compose up` (compose
refuses to start without it). The existing `orgtree-hub-data` volume keeps
its role, so an upgraded deployment imports its v1 store on the first start.
The image holds only the binary (no Python); the healthcheck runs
`orgtree-mailhub healthcheck`.

Backup: stop the hub, then back up BOTH volumes — the database (e.g.
`docker exec orgtree-mailhub-db pg_dump -U mailhub mailhub > hub.sql`, or the
volume copy procedure in OPERATIONS.md) and `orgtree-hub-data` (blobs). A
database and a blob folder from different moments can disagree: a message may
name a blob that is gone (its download answers 410) or a blob may have no row
(it is never served).

## Deliberate differences from v1

Everything else was compared with v1 directly (see Verification). These
differ on purpose:

| # | v1 | v2 | why | measured? |
|---|---|---|---|---|
| 1 | FastAPI's generated `/docs`, `/redoc`, `/openapi.json` were served | 404 | framework artefacts, never part of the protocol | yes (differential) |
| 2 | U+0000 (NUL) in stored text was kept | removed from stored text (bodies, names, blurbs, kinds, thread ids, claimed times, attachment names); a message id with a NUL is refused 422 | PostgreSQL text cannot hold NUL; Orgtree's engine strips it the same way; stripping an id could collide with another id, so it is refused instead | yes |
| 3 | a `/ui/messages` `before_at` that is not a timestamp was compared as a string | 422 `before_at is not a timestamp` | the cursor is a hub timestamp; only the bundled page sends it | yes |
| 4 | with `HUB_PUBLIC`, the app's startup ran once per listener: two startup lines and two retention sweeps | one startup line, one sweep | a v1 artefact of running the app twice | yes |
| 5 | a request that crashed the handler (500) had no request line | it has one | operators should see failures | yes |
| 6 | a poll answer carried every queued message | at most 500; the next poll returns the rest at once | bounded answers; at-least-once and ordering are unchanged | yes (v2_behaviour) |
| 7 | parked polls re-checked twice a second | woken at once for their own address (ms instead of up to 500 ms) | per-address wake-ups instead of one global counter | yes (6–22 ms) |
| 8 | a client that hung up mid-poll still counted as parked until the poll's deadline | it stops counting at once; presence rests on the 90-second window as for any client | the server no longer keeps abandoned polls running | inferred |
| 9 | a JSON request body of any size was read into memory | over 32 MiB: 413 `request body too large` | bounded memory (a body is cut to 20,000 characters either way) | yes |
| 10 | JSON bodies could be UTF-16/32 with a BOM, or use `NaN`/`Infinity` | UTF-8 JSON only (others answer 500 as other malformed bodies did) | no client sends them | inferred |
| 11 | an attachment id that reduced to nothing resolved to the blob directory (a recorded v1 gap) | it has no path at all | the gap v1's suite carried | yes (suite) |
| 12 | partial uploads left by a killed hub stayed on disk | removed at startup | no upload can be in flight before the listeners open | yes |
| 13 | several hub processes could share one SQLite store | a second process refuses to start | presence and wake-ups are per process | yes |
| 14 | `ETag` was an md5 of Python's float mtime | a different opaque value | no client uses it; `Last-Modified` keeps v1's format | inferred |
| 15 | the public listener's port was fixed at 7371 | `HUB_PUBLIC_PORT` (default 7371) | hosts and tests running several hubs | — |
| 16 | compose did not pass `HUB_ORG_RETENTION_DAYS` although `.env.example` offered it | passed | a v1 compose bug | — |
| 17 | the image ran Python; the healthcheck was a second Python | one binary; `orgtree-mailhub healthcheck` | the rewrite | yes (verify-docker) |
| 18 | `kind: "person"` at registration was stored as `org` | kept as `person` (roster, `/ui/data`, the page's tag) | Hubchat's people (G2) | yes (people_and_replies; differential) |
| 19 | `reply_to` on a send was ignored | stored and delivered (an envelope key only on messages that carry one); a value that is not a string, is longer than 4096 characters or holds a NUL is refused 422 | inline replies (G3) | yes |
| 20 | `POST /api/profile`, `POST /api/sync`, `GET /api/devices` were 404 | the additions ([v2-additions.md](v2-additions.md)) | profiles (G2), every device gets everything (G1) | yes |
| 21 | `/healthz` reported `ok`, `name`, `orgs`, `queued`, `retention_days`, `max_attachment_bytes` | also `version` and `features` (the additions it serves) | clients can tell what a hub supports without probing | yes (the side-by-side run checks them and compares the rest) |

Kept on purpose although odd (v1 behaviour clients may rely on): the two
different 401 sentences, Python `repr` quoting in refusal texts, `str()` of
non-string fields, pydantic-shaped 422s for bad query numbers, 500 with
plain-text `Internal Server Error` for a malformed request body, the
20,000-character body cut, the first payload winning a duplicate send,
receipts marked pushed when returned, Starlette's Range handling (including
multipart/byteranges and its 400/416 refusals), Content-Disposition as
Starlette writes it, redirects to the slash-twin of a path (307), 405 with
`Allow`, WebSocket handshakes refused 403 before the request log, and the
unauthenticated operator page on the full port.

## Logging

stdout carries v1's JSON lines byte for byte (startup, one per request with
`ts`, `path`, `slugs`, `status`, `ms`, and one per sweep that removed
something); `docker logs` parsers keep working. stderr carries warnings and
errors, and with `HUB_LOG_VERBOSE=1` each request's span, the handler and
its steps with their arguments and returns, and every SQL statement (never
its parameters). Secrets are never logged.

## Verification

All against throwaway databases and data folders; nothing touches a real hub.
`HUB_TEST_PG` names a folder with PostgreSQL's `bin/` and an initdb'ed
`template/data` (superuser `hubtest`, password in `template/password.txt`),
or `HUB_TEST_DATABASE_URL` names a server where the tests may create
databases.

| command | proves |
|---|---|
| `cargo test --test hub_suite` | v1's `tests/test_hub.py`, ported check for check (63 checks) |
| `cargo test --test concurrency` | the races v1's single thread never had: one address claimed ten times at once, one upload bound by ten sends, one id sent ten times, one receipt polled ten times; 800 messages from 16 senders to 16 long-polling receivers |
| `cargo test --test v2_behaviour` | the deliberate differences above that can be measured |
| `cargo test --test people_and_replies` | the person kind, profiles and replies ([v2-additions.md](v2-additions.md)) |
| `cargo test --test differential -- --ignored` | the v1 Python hub (from git history) and v2 side by side over real sockets: 202 identical requests (195 answers agree, the 7 differences listed above that requests and logs can show), the request logs; a store built by v1 imported by v2 and read back from both (exact timestamps); `hubtool.py`'s CLI, listener and MCP server against both (transcripts agree). Needs Python with `tests/requirements.txt`. |
| `python tests/test_hubtool.py` | hubtool's own suite, against the v1 hub in process (from git history) |
| `python tools/verify-docker.py [--upgrade]` | the image and a postgres container end to end, restarts of either, the healthcheck; with `--upgrade`, a v1 container's volume imported by v2 in place |
